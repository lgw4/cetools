# Rules Data Requirements Checklist: Validated Rules Data Loading

**Purpose**: Validate the quality, completeness, and internal consistency of the
requirements governing the data schema and notation, override composition and
provenance, validation strictness and diagnostics, and licensing obligations, before
`/speckit-tasks` decomposes them into work.

**Created**: 2026-08-13

**Reviewed**: 2026-08-13 (agent-evaluated at the reviewer's request; marks pending reviewer confirmation)

**Resolved**: 2026-08-13 - all 18 open items closed by spec amendment; see [Resolution log](#resolution-log)

**Feature**: [spec.md](../spec.md)

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.

**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.

**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

**How these items were derived**: each was found by reading a design artifact against
the requirement it cites. Where `contracts/` or `plan.md` had to state a rule the spec
does not, that is recorded here as a gap in the requirements rather than as a defect in
the design.

**Result**: 40 of 40 satisfied. 22 were satisfied on first review; 18 were open findings
closed by amending `spec.md` on 2026-08-13. An item marked `[x] (design)` is satisfied
because a design artifact pins it precisely and is the appropriate home for it; an item
marked `[x] (closed)` was a genuine requirements gap and now names the requirement that
closes it.

## Requirement Completeness - File Kinds and Schema Shape

- [x] CHK001 Are the kinds of rules data file enumerated in the requirements, given that FR-002a counts the supported version "per kind of file" without stating what the kinds are? [Completeness, Spec §FR-002a]
  - **Closed.** FR-002a now names five kinds as a closed set and states why the three registries are separate kinds rather than one.
- [x] CHK002 Is a requirement stated for how a file's kind is determined, given that FR-001 requires only a declared version while composition by basename leaves an added file with no packaged slot to inherit a kind from? [Gap, Spec §FR-001, §FR-032]
  - **Closed.** FR-001a requires the declaration, states why nothing outside the file can supply it, and adds the replacement-kind-must-match rule.
- [x] CHK003 Are the required and optional elements of a career file enumerated, given FR-019 requires rejecting a career that "omits any element the schema requires" without the requirements stating which those are? [Gap, Spec §FR-019]
  - **Closed.** FR-014 through FR-017 changed from "MUST be able to declare" to obligations with required and optional marked, and FR-019 now carries the enumeration explicitly.
- [x] CHK004 Is it specified which of the five throws named in FR-014 a career must declare and which it may omit? [Completeness, Spec §FR-014]
  - **Closed.** FR-014: four required, commission optional, and its absence is how a career without one is expressed.
- [x] CHK005 Are the skill tables a career may declare enumerated, and is it specified which are required and which may bear a characteristic gate? [Completeness, Spec §FR-015]
  - **Closed.** FR-015 names four tables, marks advanced education optional, and makes the gate optional on any table rather than fixed to one. This closed a divergence, not only a gap: the spec had named three.
- [x] CHK006 Are uniqueness requirements defined for rank ladder names and for rank positions within a ladder, given FR-016 admits more than one ladder? [Gap, Spec §FR-016]
  - **Closed.** FR-016 requires at least one ladder, at least one rank per ladder, distinct ladder names, and distinct non-negative rank positions.
- [x] CHK007 Are cardinality requirements defined for table contents (minimum and maximum entries), or is their absence recorded as a deliberate exclusion? [Gap, Spec §FR-015, §FR-017]
  - **Satisfied (design).** Research R13 records "No table length constraint" with a Principle V rationale: table length is the generator's business, and pinning it here would put a rules constant in engine code. FR-015 and FR-017 now carry the non-empty floor and repeat the no-maximum reasoning.
- [x] CHK008 Are value-range requirements specified for the plain numeric fields FR-004a introduces - throw targets, mustering-out cash amounts, and rank positions? [Gap, Spec §FR-004a]
  - **Closed.** FR-014 requires a positive throw target, FR-017 non-negative cash, FR-016 non-negative rank positions.
- [x] CHK009 Is it specified whether the skills registry expresses "has no specialties" as an empty list or as an absent key, given FR-011 requires each skill to declare whether it has them? [Clarity, Spec §FR-011]
  - **Satisfied.** FR-011's "declare ... whether it has specialties" does the work, and `contracts/data-files.md` makes the consequence explicit: the list is required and empty, because "a missing key is indistinguishable from a forgotten one".

## Requirement Clarity - The Compact Notation

- [x] CHK010 Are the characters admissible in a name defined, given that source-material skill names carry spaces, apostrophes, slashes, and hyphens and so cannot be tokenized on whitespace? [Gap, Spec §FR-004]
  - **Satisfied (design).** `contracts/notation.md` defines `text` as any run of characters other than parentheses, trimmed. Grammar detail is the contract's proper home.
- [x] CHK011 Is a disambiguation order among the four notation forms specified, so that an entry matching more than one form has one defined reading? [Ambiguity, Spec §FR-004]
  - **Satisfied (design).** Research R9 fixes a tail-anchored order, notes the order matters only between rules 1 and 3, pins it anyway against future reordering, and records the residual trap (a name ending in a digit reads as a grant).
- [x] CHK012 Is it specified which of the four forms are admissible in each notation-bearing field, given FR-009 requires reporting "the forms that were acceptable in that position"? [Gap, Spec §FR-009]
  - **Closed.** FR-009a defines the three admissible-form subsets and makes a well-formed entry in the wrong context a rejection. FR-005 was reworded to scope "and no other" to bare names, resolving the apparent conflict with the benefit table's dual-registry validation.
- [x] CHK013 Is case sensitivity specified for matching skill names, benefit item names, and characteristic codes against their registries? [Gap, Spec §FR-013]
  - **Closed.** FR-013 now requires exact, case-sensitive matching for every name in every registry, with the reasoning `data-model.md` gave for characteristics generalized.
- [x] CHK014 Is "malformed" defined by enumeration or by exclusion from the admissible forms, so that a shape nobody anticipated has a predictable classification? [Measurability, Spec §FR-009]
  - **Satisfied (design).** The grammar in `contracts/notation.md` is the operative definition by exclusion; the nine-row malformed table illustrates rather than bounds.

## Requirement Completeness - Override Composition

- [x] CHK015 Do FR-029's requirement that an override "mirror the layout of the packaged data" and FR-040a's basename-only positioning express the same composition rule, or can one file's position differ between a directory load and a single-file validation? [Conflict, Spec §FR-029, §FR-040a]
  - **Closed, by decision.** FR-029 rewritten: basename positioning is the general rule, layout mirroring is RECOMMENDED and not required. FR-040a retained as the common case but restated as a consequence rather than an exception. Recorded in Clarifications. `research.md` R3 now matches the requirement rather than exceeding it.
- [x] CHK016 Is it specified whether an override location is traversed recursively, and whether a file's depth within it affects the position it takes? [Gap, Spec §FR-029]
  - **Satisfied (design), reinforced.** `contracts/data-files.md` Composition rule 2 specifies the traversal; FR-029 now states depth-independence in the spec itself.
- [x] CHK017 Are requirements defined for two files in one override location that resolve to the same position? [Gap, Spec §FR-029]
  - **Satisfied (design), promoted.** Composition rule 5 had it; FR-029a now states it, together with the packaged-basename-uniqueness precondition that `plan.md` had flagged as a test.
- [x] CHK018 Is it specified whether the override location that FR-042 requires of every resolving command may itself be a single file, or whether single-file input is a property of the validation command alone? [Ambiguity, Spec §FR-040a, §FR-042]
  - **Satisfied (design), promoted.** FR-028 now states that an override location may be a directory or a single file and that both compose by one rule. The former Assumptions entry was updated to point at the requirement.
- [x] CHK019 Are requirements defined for files in an override location that are not rules data files at all? [Gap, Spec §FR-032]
  - **Closed, by decision, twice.** FR-032a first made such a file a rejection; that was revised after review found it would fail a load over a `.DS_Store`. It now names the file as ignored in the provenance report without failing the load, which is symmetric with FR-032's treatment of a misspelled stem, and FR-032b passes dot-prefixed files over in silence as tool-made rather than authored.
- [x] CHK020 Is a requirement stated that a data set must contain each registry, given that FR-030's whole-file replacement provides no way to distinguish a registry that is absent from one that was never overridden? [Gap, Spec §FR-030, §FR-010]
  - **Satisfied (design), promoted.** FR-010a now requires every single-instance kind to be present, alongside the duplicate rule.
- [x] CHK021 Does FR-019b's duplicate-name rule have a stated analogue for two files in force claiming the same registry role? [Gap, Spec §FR-019b]
  - **Closed.** FR-010a states it for all four single-instance kinds, with the misspelled-registry-filename rationale `data-model.md` gave.

## Provenance and Reproducibility

- [x] CHK022 Is it specified whether provenance identifies the package version, given FR-034 rests the packaged case on the package version determining content exactly while FR-035 reports only the overridden files? [Gap, Spec §FR-034, §FR-035]
  - **Closed, by decision.** FR-033a requires the version in every provenance report; FR-034 and FR-035 amended to match; SC-008 extended; Acceptance Scenario 4.1 and the Provenance entity updated.
- [x] CHK023 Is the fingerprint's required strength, or its reproducibility by the person handed a result, specified - or only that it varies with content and nothing else? [Clarity, Spec §FR-036]
  - **Satisfied (design).** Research R4: SHA-256 over raw bytes, full digest, algorithm named in the value so a later change is visible, chosen so `shasum -a 256` reproduces it. The line-endings consequence is recorded and accepted.
- [x] CHK024 Are requirements defined for what provenance reports when an override location was supplied but contributed no file? [Coverage, Spec §FR-033, Edge Cases]
  - **Satisfied.** The spec's Edge Cases covers it directly: an empty override location "loads the shipped data set unchanged, and reports its provenance as packaged".
- [x] CHK025 Is the placement and form of the provenance report in each output mode specified precisely enough for FR-045's "exactly one permitted difference" to be judged objectively? [Measurability, Spec §FR-037, §FR-045]
  - **Satisfied (design).** `contracts/cli.md` fixes the block and its position after `Seed:`; `contracts/json-output.md` appends one key with fixed order; research R12 specifies verification against frozen pre-loader goldens. The version added by FR-033a sits inside that same block, so the "one addition" claim is unaffected.

## Validation Strictness and Diagnostics

- [x] CHK026 Is "location within that file" defined at a specific granularity - key path, line, or offset - given SC-002 requires every rejection to name it? [Measurability, Spec §FR-022, §SC-002]
  - **Satisfied (design).** `data-model.md`: dotted key path with array indices, e.g. `tables.service.entries[2]`; `""` for a whole-file problem, with TOML line and column carried in `found` instead. SC-002 now says "where the problem is not about the file as a whole", matching that.
- [x] CHK027 Is an ordering requirement stated for collected problems, so that one data set yields the same problems in the same sequence on every run? [Gap, Spec §FR-021]
  - **Satisfied (design).** Sorted by `(file, location)`, stated in `data-model.md`, `contracts/json-output.md`, and `contracts/cli.md`; research R5 sorts the packaged walk for cross-platform stability.
- [x] CHK028 Are requirements defined for bounding or grouping a cascade, such as an absent skills registry rendering every skill name in every career unrecognized? [Gap, Spec §FR-021, §SC-003]
  - **Closed as a recorded deferral.** Out of Scope now carries the exclusion with its cost stated, why suppression is the wrong cure (it hides a real second problem behind a guess), and which later feature should revisit it with evidence this one lacks.
- [x] CHK029 Are the exit statuses the validation command may produce enumerated, and is a usage error - a named override location that does not exist - distinguished from a validation failure? [Gap, Spec §FR-041, §SC-010]
  - **Satisfied (design).** `contracts/cli.md` enumerates 0/1/2 and names the set SC-010 leaves as an unresolved reference. Streams are specified too: problems to stdout, usage errors to stderr.
- [x] CHK030 Is stability or versioning specified for the machine-readable problem shape, given it is promised as consumable without parsing prose? [Gap, Spec §FR-041]
  - **Satisfied (design).** `contracts/json-output.md` commits the shape with key order fixed and a `kind` discriminator, pinned by contract tests, and draws the stability boundary explicitly: `found` and `expected` are fixed as distinct fields, "not their wording".
- [x] CHK031 Is it specified whether a data set may be re-read within one process, given User Story 2's authoring loop edits and re-validates and FR-027 forbids consulting anything the caller did not name? [Gap, Spec §FR-027]
  - **Satisfied (design).** Research R13 and `contracts/library-api.md`: the packaged load is cached, an override load is not, "because a caller may edit the file and load again in the same process, which is the authoring loop".

## Resolution log

Amendments made to `spec.md` on 2026-08-13 in response to the 18 open items. Three
required a decision from the reviewer and are recorded in the spec's Clarifications under
**Session 2026-08-13 (requirements checklist review)**.

**Requirements added** (10): FR-001a (kind declaration), FR-009a (admissible forms per
context), FR-010a (single-instance kinds present and unique), FR-020a (unreadable or
malformed file), FR-020b (wrong type), FR-029a (basename uniqueness and collision),
FR-032a (non-data file in an override, named as ignored), FR-032b (dot-prefixed files
passed over silently), FR-033a (package version in provenance), FR-047 (copyright notice
chain coverage).

**Requirements amended** (15): FR-002a, FR-005, FR-013, FR-014, FR-015, FR-016, FR-017,
FR-019, FR-028, FR-029, FR-031, FR-034, FR-035, FR-040a, FR-046.

**Success criteria**: SC-002 rewritten as a closed, requirement-mapped list of twelve
rejection categories, with the ignored-file case explicitly excluded and pointed at SC-005;
SC-005 extended to cover the three ways a file can fail to take effect; SC-008 extended
with the version and its direct assertion; SC-009 extended with placeholder substitution;
SC-015 and SC-016 added.

**Elsewhere**: Acceptance Scenario 4.1; five Edge Cases (flat override layout, misspelled
registry filename, non-data file in an override, tool-made file); Key Entities (Kind added;
Data file, Schema version, Career definition, Provenance revised); one Out of Scope entry
(cascade grouping, deferred with reasons); one Assumptions entry retired into the
requirement it became.

**Follow-up decisions, both resolved 2026-08-13.**

- *Stray files.* FR-032a as first written rejected any non-data file, which would have
  failed a load over a `.DS_Store` on macOS. Revised to report rather than reject, with
  FR-032b carving out dot-prefixed files. The revision restored symmetry with FR-032, which
  had always answered a misspelled filename with visibility rather than rejection; the
  original wording was the departure.
- *Version in reference outputs.* FR-033a would have embedded a CalVer string in every
  committed check output, rewriting them all on each release and giving each rewrite an
  occasion to absorb an unrelated change, which is what SC-009 exists to prevent. Reference
  outputs now hold the version as a placeholder substituted at comparison time, and SC-008
  asserts the reported version against the installed package version directly.

**Downstream artifacts now stale.** The amendments changed behavior the design already
specified, so `plan.md`, `research.md`, `data-model.md`, and three contracts need a pass
before task generation. See the notes handed back with this review.

## Notes

- Add findings inline beneath an item rather than editing the item text, so the numbering stays stable across review rounds
