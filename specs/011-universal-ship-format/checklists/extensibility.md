# Data-Driven Extensibility Checklist: Universal Ship Description Format

**Purpose**: Requirements-quality review gate for Constitution Principle V — validate that FR-028a, FR-030, FR-030a, FR-031 and SC-007 pin down exactly which rules-data rows gain which columns, what "no renderer change" means as an acceptance criterion, and how the tech-level derivation stays open to new rows. These items test the *requirements*, not the tables.
**Created**: 2026-07-24
**Feature**: [spec.md](../spec.md)

**Scope of review**: `spec.md` with `data-model.md` §3–§4 and `contracts/engine-api.md` as requirement sources. The constitution states that adding new game content must require only a new data-structure instance, with zero changes to engine logic.

**Cross-check status (2026-07-24)**: All 30 items reviewed. **All 30 resolved** — 16 required a `spec.md` edit, made the same day; 14 were already answered by a design artifact that is the right home for the answer. Two findings mattered: FR-028a enumerated categories (hulls, drives, fittings) for which the SRD tabulates no tech level at all, inviting an invented value (CHK010); and FR-031 never said what "editing the renderer" means, leaving SC-007 — the one success criterion that can fail silently — unmeasurable (CHK018, CHK019).

## Column Coverage — Completeness

- [x] CHK001 Does the requirement set name every table that gains a display name, and every table that does not, so a reader can tell an exclusion from an oversight? [Completeness, Spec §FR-030] → **Fixed**: FR-030 lists the tables that gain a display name and, after this review, no longer lists one that no sentence spells. data-model §4 tables the exclusions with the reason for each, so a reader can tell an exclusion from an oversight.
- [x] CHK002 Is a *plural* spelling required alongside the display name for rows that appear after a count, or is FR-030's "display name used in prose" a single string? [Gap, Spec §FR-030, §FR-023] → **Fixed**: FR-030 now requires the plural spelling wherever the paragraph can state a count, with the reason: the SRD's plurals are not uniformly regular.
- [x] CHK003 Is it specified whether hulls, drives and quarters need display names, given the sentence requirements never name them as catalog items? [Clarity, Spec §FR-030] → **Resolved**: data-model §4 states that hulls, drives and quarters need none — they are never named in prose as catalog items — and gives that as the reason rather than leaving the row blank.
- [x] CHK004 Is a cockpit display name required by any sentence, given FR-030 lists cockpits but FR-027 only requires the word "cockpit"? [Consistency, Spec §FR-030, §FR-027] → **Fixed**: it was not. Cockpits are removed from FR-030's list: FR-027 needs only the word "cockpit", which is a hull-class distinction rather than a component spelling. data-model §4 drops the column.
- [x] CHK005 Does FR-030a specify the DM's storage form — signed integer, string with sign, or unsigned with a separate sign rule? [Clarity, Spec §FR-030a, §FR-009] → **Resolved**: correctly a data-shape decision: data-model §4 stores `dm` as a signed integer and `prose.signed()` renders the sign, which is what FR-009's "explicit sign at every magnitude" requires. FR-030a needs only that the modifier be data.
- [x] CHK006 Does the requirement set specify the columns needed to render a fuel processor's throughput, or only that the throughput MUST be stated? [Gap, Spec §FR-017, §FR-031] → **Resolved**: data-model §4 names `unrefined_fuel_per_ton`, and FR-017 now states the SRD rate (20 tons per ton per day), so the column's value is sourced by the spec rather than by the design doc.
- [x] CHK007 Are the columns needed to identify a hangar specified, so the hangars sentence and the special-features sentence can partition the fittings without a key comparison? [Gap, Spec §FR-014, §FR-017, §FR-031] → **Fixed**: FR-031 now forbids recognising a component by its key, which forces identification onto a column. data-model §4 names the existing `tons_per_vehicle_ton` as that column, so the hangars sentence and the special-features sentence partition the fittings from data.
- [x] CHK008 Are crew position spellings and their print order specified as data, given FR-018 requires a breakdown and FR-031 forbids hardcoded wording? [Gap, Spec §FR-018, §FR-031] → **Fixed**: FR-018 enumerates the seven positions and fixes their order, and FR-031 forbids hardcoded wording; data-model §4 carries them as `CREW_POSITIONS`, with an invariant test tying each row to a `Crew` field.
- [x] CHK009 Is the hull-configuration display name's home specified, given the configuration table currently carries only a cost modifier? [Gap, Spec §FR-030, §FR-016] → **Resolved**: data-model §4 gives it a home: `CONFIG_MODIFIERS` becomes `CONFIGURATIONS`, keyed identically, carrying the name beside the cost modifier.

## Tech Level Derivation

- [x] CHK010 Does FR-028a's list of contributing categories match the set of categories the SRD actually tabulates, or does it name categories the SRD leaves blank? [Consistency, Spec §FR-028a] → **Fixed**: it did not — FR-028a named hulls, drives and fittings, for which the SRD tabulates nothing. FR-028a no longer enumerates categories; it states the rule and makes the category audit a finding from reading every table, which research §D is.
- [x] CHK011 Is "contributes nothing" specified at row granularity as well as category granularity, for a table where one row's tech level is blank? [Gap, Spec §FR-028a] → **Fixed**: FR-028a now covers an individual row whose tech-level cell the SRD leaves blank, distinct from an untabulated category — the fixed mounting's literal "-".
- [x] CHK012 Is the derivation stated as a rule over *fitted* components, rather than as a fixed list of categories to inspect — so a new category with a tech level widens it automatically? [Clarity, Spec §FR-028a, §SC-007] → **Fixed**: FR-028a states the rule over the components fitted rather than over a list of categories to inspect, and SC-007 now requires a new row to produce a correct *derived tech level* as well as correct wording, which is the testable form of "widens automatically".
- [x] CHK013 Is the derivation's result type specified — always a value, or absent when nothing contributes? [Gap, Spec §FR-028] → **Fixed**: new FR-028c — a derived tech level MUST always exist, so the result is a value and never an absence.
- [x] CHK014 Is it specified whether a component that is *installed but free* (the Standard electronics package included in the bridge) contributes to the derivation? [Gap, Spec §FR-028a] → **Fixed**: FR-028c answers it directly: the standard electronics package is included in the bridge or cockpit, and the derivation reads its tech level like any other. Free does not mean absent.
- [x] CHK015 Is the derived value's home specified — computed once on the built ship, or recomputed at render time? [Clarity, Spec §FR-028, §FR-003] → **Resolved**: data-model §3 and §6 put it on the built ship, computed once; FR-003 requires rendering be a pure function of the built ship, which the design honours by leaving the renderer no derivation to perform.
- [x] CHK016 Is FR-028b's "used as given, never re-checked" stated strongly enough that no validation may be added later, including a warning? [Clarity, Spec §FR-028b] → **Fixed**: FR-028b now says the system "does not re-check, warn about, or clamp" an explicit value, closing the three ways a later change could weaken it.
- [x] CHK017 Is the interaction between an explicit tech level and the derived one specified when the explicit value is *lower* than derived, as well as higher? [Coverage, Spec §FR-028b] → **Fixed**: FR-028b now covers both directions — "whether it is higher or lower than the derived value".

## Renderer Independence

- [x] CHK018 Does FR-031 define what counts as "editing the renderer" — a new branch, a new string literal, a new key comparison? [Measurability, Spec §FR-031] → **Fixed**: FR-031 defines it: adding a branch, adding a string literal that names a component, or comparing against a component's key. Without this, SC-007 was the one success criterion that could fail silently.
- [x] CHK019 Is FR-031 stated to cover *identification* of a component kind as well as its wording, so a key comparison (`kind == "vehicle_hangar"`) is as prohibited as a hardcoded name? [Clarity, Spec §FR-031] → **Fixed**: FR-031's closing clause covers identification explicitly — a component's kind MUST be recognised by a column on its row, never by the spelling of its key.
- [x] CHK020 Does SC-007 specify what a new row must carry to be renderable, so "correct wording" is decidable rather than aspirational? [Measurability, Spec §SC-007] → **Fixed**: SC-007 now names what a row must carry: the display name, the plural where the paragraph can count it, and the tech level where the SRD tabulates one.
- [x] CHK021 Is SC-007 scoped to rows in existing tables, or does it also claim that a new *sentence-worthy component category* needs no renderer change? [Clarity, Spec §SC-007] → **Fixed**: SC-007 is scoped to "a new component **row** to the rules data". A new sentence-worthy *category* would need a new sentence, which is a spec change, not a data edit.
- [x] CHK022 Is a requirement stated that a component's wording must come from the row of the component actually fitted, rather than from a lookup the renderer performs by name? [Clarity, Spec §FR-031] → **Fixed**: FR-031 — the wording for a component MUST come from its data row, and a key comparison is named as an edit to the renderer, so a lookup by name cannot substitute.
- [x] CHK023 Are requirements defined for a row that is added with a display name but no plural, or with a tech level but no name — that is, is row well-formedness specified? [Gap, Spec §FR-030, §SC-007] → **Fixed**: SC-007 states the columns a row must carry to be renderable, which is row well-formedness expressed as an acceptance criterion; data-model §4 lists the matching invariant tests (every nameable row named, every counted row pluralised, every ammunition row pointing at a real weapon).
- [x] CHK024 Is the ammunition-to-weapon relationship specified as data, given the ammunition sentence must name the weapon its rounds feed? [Gap, Spec §FR-012, §FR-031] → **Fixed**: FR-012a requires each ammunition clause to name the weapon its rounds feed, and FR-031 forbids the renderer knowing that missiles go in missile racks; data-model §4 makes the link a `weapon` column on the ammunition row.

## Consistency with Existing Data Contracts

- [x] CHK025 Is it explicit that display names are presentation only, and that design-file keys (`sand_barrels`, `vehicle_hangar`) do not change? [Consistency, Spec §FR-033, §FR-030] → **Resolved**: contracts/design-schema.md states it under "What does not change": `sand_barrels` stays the ammunition kind a design writes even though the paragraph says canisters, and `vehicle_hangar` stays the fitting kind even though the paragraph says small craft hangar.
- [x] CHK026 Is the renaming of any existing column, or the removal of any existing table, stated as a requirement rather than left to the implementation? [Gap, Spec §FR-032] → **Resolved**: correctly a design decision, not a requirement: FR-032 governs computed *values*, and none changes. data-model §8 lists the removals and the rename so they are reviewable in one place.
- [x] CHK027 Do the new columns preserve FR-032's guarantee, given that at least one existing table (`CONFIG_MODIFIERS`) is read by costing? [Consistency, Spec §FR-032] → **Resolved**: data-model §4 pins it: `Configuration.cost_modifier` reads the new table and returns the same three values, so no builder arithmetic changes and FR-032 holds.
- [x] CHK028 Are the invariants a reviewer could check on the new columns stated — every nameable row named, every counted row pluralised, every ammunition row pointing at a real weapon? [Measurability, Spec §FR-030, §SC-007] → **Resolved**: data-model §4 states them as invariant tests in `tests/test_ship_tables.py`, which is where a reviewer can actually run them.
- [x] CHK029 Is the existing decision to omit unpriced SRD entries (the beam laser) reconciled with a requirement set that now also demands display names and tech levels for every catalog row? [Consistency, CONTEXT.md, Spec §FR-030] → **Resolved**: no tension: FR-030 governs rows that exist, and an omitted row needs no name. The beam laser is omitted because the SRD prices it nowhere — the same discipline FR-030 now applies to display names.
- [x] CHK030 Is the previously-documented status of `ArmorRow.min_tl` and `ComputerRow.tl` as "stored for table fidelity but checked nowhere" updated by this feature's requirements, or left contradicting them? [Conflict, CONTEXT.md, Spec §FR-028a] → **Fixed**: recorded as an implementation obligation in plan.md's file list, naming the sentence to retire — CONTEXT.md's claim that armour and computer tech levels are "checked nowhere, since v1 has no tech-level model" goes false the moment this feature builds that model, and `check_docs.py` cannot catch a prose claim that has merely gone stale.

## Notes

- Check items off as reviewed: `[x]`, appending `→ **Resolved**: …` or `→ **Fixed**: …` with the change made.
